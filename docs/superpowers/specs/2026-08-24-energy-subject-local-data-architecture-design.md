# 能源主体本地数据与授权协同架构设计

**日期：** 2026-08-24  
**状态：** 待用户审阅  
**范围：** `hiddenchain-platform` 前端、后端、本地节点协议、模拟数据和 Render/GitHub 发布边界

## 1. 已确认的目标

系统采用“中央控制平台 + 各能源主体本地数据节点”的架构。

- 电力企业、煤炭企业、热能企业、天然气企业、石油企业等均是独立数据主体。
- `energy_domain` 表示能源领域，`org_id` 表示实际数据租户。
- 各主体的原始数据只能保存在自己的内网或服务器。
- 企业之间、不同能源领域之间不能互相直接查看数据。
- 现有 `REGULATOR` 角色继续代表能源局，不新增 `ENERGY_BUREAU` 角色。
- `REGULATOR` 是唯一可以发起跨主体数据申请的角色，但不能绕过规则或企业审批。
- 现有结算、交易协同和审计功能保留，只重做数据边界、授权链路和结果分发。

## 2. 非目标与边界

本次改造不承诺：

- 证明企业上传前的数据绝对真实；
- 建设法院或市场监管机构的商业造假识别流程；
- 把所有主体部署成完整独立的平台；
- 把真实企业数据部署到 GitHub、Render 或中央平台；
- 让 Agent 生成或修改正式能源数值、结算金额或授权决定。

平台只保证：数据上传后不可被悄悄修改，授权和计算过程可追溯，正式结果来自企业本地的确定性计算。

## 3. 总体架构

```text
┌──────────────────────────────────────────────┐
│ 中央控制平台                                 │
│ React + FastAPI                              │
│                                              │
│ 用户/组织/权限 · 数据目录 · 申请/审批         │
│ 规则登记 · 结算任务元数据 · 结果凭证          │
│ 按范围展示存证 · 节点注册 · 运行状态          │
└──────────────────────┬───────────────────────┘
                       │ 签名请求 / 签名结果
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
┌────────────┐  ┌────────────┐  ┌────────────┐
│主体 A 本地节点│  │主体 B 本地节点│  │主体 C 本地节点│
│原始数据      │  │原始数据      │  │原始数据      │
│本地规则      │  │本地规则      │  │本地规则      │
│本地计算      │  │本地计算      │  │本地计算      │
│完整存证      │  │完整存证      │  │完整存证      │
└────────────┘  └────────────┘  └────────────┘
```

中央平台保存目录和凭证，不保存主体原始数据。主体本地节点保存原始数据、本地规则判断、确定性计算和完整本地审计记录。

本地开发和 Render 演示环境可以使用多个独立容器和独立 SQLite 文件模拟多个主体节点；这不改变正式部署时“每个主体自己管理节点”的边界。

## 4. 核心数据流

### 4.1 数据目录发布

1. 主体在本地节点登记数据资源。
2. 本地节点向中央平台发布最小目录信息：数据名称、时间范围、可计算指标、开放方式和状态。
3. 中央平台只保存目录元数据、目录哈希和节点引用。
4. `REGULATOR` 可以查看全局目录，但看不到具体数值。
5. 其他能源主体只能查看自己的目录，以及业务流程明确授权给它的目录信息。

### 4.2 预设规则自动调用

1. 主体内部有相应权限的人员发布规则。
2. 规则规定可调用的数据指标、时间范围、统计粒度、调用频率、最小数据量和输出格式。
3. 规则分为三种开放方式：规则自动调用、企业审批后调用、禁止对外调用。
4. 没有规则的数据默认需要企业审批。
5. `REGULATOR` 在前端确认请求后，中央平台生成带签名、时间戳和随机数的调用请求。
6. 本地节点校验请求、规则、调用预算和防重放信息。
7. 本地确定性计算只返回聚合、统计、趋势或脱敏结果，以及签名结果凭证。
8. 中央平台保存执行回执和存证摘要，不保存原始数据。

### 4.3 临时申请

1. `REGULATOR` 通过页面或 Agent 形成结构化申请。
2. 一次涉及多个主体的总申请，在中央平台拆成独立的主体子申请。
3. 每个主体独立审批、拒绝或撤销。
4. 本地节点仅对已批准的子申请执行。
5. 多主体汇总只有在全部必要主体批准时才生成完整结果；若业务允许部分结果，则明确标注缺失主体，不能冒充全量结果。

### 4.4 结算和交易协同

现有结算任务保留。参与方通过任务关系和数据合同协同，但不能直接读取其他主体的原始数据。每个主体本地提供授权后的受控结果或计算回执，中央平台负责任务状态、结果确认和按范围分发存证。

数据上传错误时不允许覆盖、修改或追加更正版本。只能重新上传并重新发起新的结算任务。新任务不与旧任务建立系统关联，也不复用旧任务的授权、状态或结果。

### 4.5 Agent

Agent 只负责：

- 解析自然语言需求；
- 识别企业、时间范围和指标；
- 生成主体子申请草案；
- 展示预览；
- 在人工确认后提交正式申请；
- 对已产生的结果做解释。

Agent 不得批准申请、读取原始数据、扩大查询范围、修改正式结果或绕过本地节点。

系统只记录 `REGULATOR` 人员最终确认并提交的正式操作和后续执行记录，不持久化 Agent 的中间思考过程。

## 5. 后端模型和权限

### 5.1 复用现有模型

继续复用现有 `Organization`、`User`、`SettlementTask`、`DataUsageRequest`、`DataContract`、数据资产和证据模型。新增或强化以下边界对象：

- `LocalNode`：主体节点、公钥、地址、能力和在线状态；
- `DataCatalog`：目录元数据和目录哈希；
- `AccessRule`：规则内容、版本、开放方式、生效/撤销状态；
- `RequestItem`：总申请拆分出的主体子申请；
- `ExecutionReceipt`：本地节点签名的计算结果和执行摘要；
- `EvidenceScope`：存证归属主体、任务、可见角色/用户、字段范围和有效期。

中央数据库中的 `DataUpload` 只能保存元数据、哈希、节点引用和质量信息。原始载荷不得进入中央业务库或中央 Vault。

### 5.2 简单权限档位

权限不做字段级碎片化，使用组织内用户授权的简单权限：

- `VIEW_DATA`：直接查看允许范围内的结果或本组织数据；
- `REQUEST_DATA`：不能直接查看，必须发起申请；
- `APPROVE_AUTHORIZATION`：可以批准本组织收到的能源局申请；
- `MANAGE_RULES`：发布、暂停和撤销本组织规则；
- `MANAGE_MEMBERS`：分配和收回组织内用户权限。

组织负责人或具有成员管理权限的用户为具体人员分配和撤销权限。普通用户没有默认审批能力。权限变化进入审计记录。

### 5.3 角色边界

- `REGULATOR`：能源局，可查看全局目录、发起跨主体申请、查看授权结果和监管存证；不能默认查看数据值。
- 能源企业角色：只管理和查看本组织数据，或查看自己参与任务中的必要结果。
- `EXCHANGE`：继续组织结算和交易任务，但不能因为交易中心身份取得企业原始数据。
- `ADMIN`：运维平台、节点和系统状态，不得查看企业原始数据，不能绕过授权。

后端是最终安全边界。前端菜单隐藏、路由限制和按钮状态都不能代替后端授权判断。

## 6. 前端工作台

保持一个 React 应用和现有整体视觉系统，登录后按角色、组织和权限显示内容。

企业主体工作台包括：我的数据目录、我的规则、待我审批、我的结算任务、我的结果和我的存证。

`REGULATOR` 工作台包括：全局数据目录、Agent 需求输入、拆分预览、人工确认、申请进度、已授权结果和监管存证。

交易参与方只看到自己参与的任务、确认事项和必要凭证。`ADMIN` 只看到运维和系统状态。

所有页面必须接真实后端接口，并完整处理草稿、待确认、已提交、等待审批、已批准、计算中、成功、失败、等待重试、已撤销和已过期状态。不能保留只显示假成功或假结果的按钮。

## 7. 存证、可见性和报告

主体本地保存完整审计记录；中央平台保存授权单、规则版本、请求摘要、结果哈希、签名、时间戳和调用回执。

存证按范围展示：

- 主体私有存证：只有本主体可见；
- 交易存证：只给同一任务的必要参与方；
- 监管存证：`REGULATOR` 只能看已授权主体、任务和字段；
- 对外报告：只展示能源局决定发布的汇总指标或报告。

原始数据永不返回中央平台、Render、GitHub 或社会访问端。

对外报告必须说明：结果基于企业上传数据，平台核验的是上传后的完整性和计算过程，不代表平台对上传前数据真实性作司法认定。

## 8. 异常和不可变数据

- 本地节点离线或超时：不返回数据，进入等待重试或失败状态；不能中央兜底。
- 重试使用同一请求编号，不能重复授权、重复使用或制造重复存证。
- 企业拒绝申请：申请结束为拒绝。
- 规则撤销：后续调用立即失败；已完成结果和审计不删除。
- 规则修改：生成新规则版本，旧版本只用于解释历史调用。
- 上传后不能修改原数据；错误只能重新发起新的结算任务。
- 旧任务保留给原参与方和有权限的 `REGULATOR` 审计查看，但不进入当前列表、统计、授权或新任务计算。

## 9. 数据重置、部署和发布

本次改造清理旧运行数据库、旧本地数据仓库、旧结算/授权/审计记录和旧模拟数据；保留代码、文档、测试、设计资料、账号和角色。之后重新生成全新的模拟数据。

GitHub 只保存代码、配置模板、测试文件和模拟数据，不保存真实数据、运行数据库、密钥或密码。

Render 只部署中央控制平台和模拟节点，使用全新模拟数据，不承载真实企业节点或真实生产数据。正式企业节点由各主体在自己的内网或服务器部署和管理。

## 10. 测试和验收

必须覆盖以下端到端场景：

1. 企业只能看到自己的数据。
2. 不同企业、不同能源领域不能互相查看。
3. `REGULATOR` 未授权前只能查看目录。
4. 命中规则才能自动调用。
5. 没有规则必须企业审批。
6. 撤销规则后新调用失败。
7. 多企业申请按企业分别审批。
8. Agent 必须人工确认后提交。
9. 本地节点离线不能返回假成功。
10. 原始数据不进入中央数据库、GitHub 或 Render。
11. 存证按权限展示。
12. 旧任务不影响新任务。
13. 前端每个按钮都能走完后端、本地节点、结果和存证链路。
14. 对外报告含有上传前真实性不属于平台司法认定的边界说明。

## 11. 已知限制

当前仓库没有真实的跨主体生产级 EDC、TEE、区块链共识或独立部署基础设施。实现阶段必须继续使用准确的能力标签：本地受控、适配器、演示或阻断；不能把本地节点模拟写成已经完成生产级可信数据空间。
