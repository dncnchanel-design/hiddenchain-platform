# 能源主体本地数据架构实施计划

## 目标

在保留现有产品视觉系统、既有账号与角色体系、`REGULATOR` 角色名称和可复用查询确认机制的前提下，把平台改成“中央控制面 + 各能源主体本地节点”的架构：

- 每个实际能源主体以 `org_id` 为数据边界，独立管理自己的数据。
- `energy_domain` 只表示能源领域，不表示数据所有权。
- 企业原始数据、完整本地审计和本地计算过程留在企业内网/服务器。
- 中央控制面只保存目录元数据、规则、请求、审批、任务元数据、哈希、签名、执行回执和按权限生成的存证投影。
- `REGULATOR` 可以查看全局目录元数据，但只有命中规则或企业批准后，才能获得本次授权范围内的聚合结果/脱敏结果。
- GitHub、Render 和演示环境只使用代码、配置模板、控制面数据和明确标注的模拟数据。

本计划采用最小必要改造：优先复用现有 `DataUsageRequest`、查询解析/确认、迁移、连接器签名和前端工作台，不另造一套平行系统。

## 实施顺序

### 1. 建立安全基线和改造护栏

先保留当前工作区所有用户已有改动，确认只修改受本计划覆盖的文件。

执行并记录基线：

```text
backend: python -m pytest -q
frontend: pnpm typecheck && pnpm test && pnpm build
```

同时记录当前迁移版本、种子数据入口、`docker-compose.yml`、`render.yaml`、`CONNECTOR_ENDPOINTS_JSON` 的现状。不得把运行时数据库、`backend/app/runtime/vault`、截图、临时报告或其他已有未跟踪文件加入提交。

新增代码必须满足以下护栏：

- 所有查询必须带 `provider_org_id`，不能只按能源领域路由。
- 中央 API 不提供原始业务数据回退读取；本地节点不可用时返回等待/失败。
- 任何“成功”响应都必须来自真实后端处理、本地节点计算和存证写入。
- 旧任务只读、留痕、从当前列表和新计算中排除；新任务生成全新 ID，不与旧任务关联。

### 2. 增加主体节点、规则、分拆请求和存证模型

#### 2.1 后端模型和迁移

在 `backend/app/models.py` 增加或补齐以下实体，字段命名以现有 SQLAlchemy 风格为准：

- `LocalSubjectNode`：`org_id`、节点标识、端点、验证公钥、启用状态、环境标记、最后健康状态。端点和公钥从环境变量/部署配置注入，数据库只保存非秘密元数据。
- `AccessRule`：主体、数据资源/指标范围、时间粒度、统计函数、最小样本量、脱敏/舍入限制、调用频率/预算、状态、版本和批准人。
- `DataRequestBatch`：一次 `REGULATOR` 业务请求的父请求、用途、法律依据、申请人、确认时间、状态、是否允许部分结果。
- `DataRequestItem`：父请求下按 `provider_org_id` 拆出的独立子请求、命中的规则版本、企业审批状态、节点执行状态、结果范围。
- `ExecutionReceipt`：请求项、节点、请求哈希、结果哈希、签名、执行时间、输出摘要、可见范围和撤销状态。
- `EvidenceProjection`：存证类型、所属主体/任务/请求项、可见主体、可见权限、投影内容或摘要。

复用现有 `DataUsageRequest` 时，增加 `provider_org_id`、父请求/请求项标识、规则版本和“原始数据不出节点”的输出约束；不删除现有历史字段。

在 `backend/app/migrations.py` 新增一次向前迁移：创建上述表、索引和必要的唯一约束。所有审批、执行和重试路径使用唯一请求项 ID + 幂等键，保证重试不重复授权、不重复计算、不重复存证。

#### 2.2 权限与主体边界

在 `backend/app/services/trust_space.py` 和相关权限辅助函数中统一执行：

- 企业、交易主体只能查询自己的 `org_id` 数据和自己参与的任务。
- 交易主体不再因为角色是 `EXCHANGE` 就获得全局资产浏览权限。
- `REGULATOR` 可浏览所有主体的目录元数据，不可因角色自动读取所有数据值、任务结果或完整审计。
- `ADMIN` 只处理平台运维和健康状态，不进入任何主体业务数据。
- 结果、任务、审计、存证接口统一调用同一套 scope helper；禁止在路由里各自写一套“放宽查询”。

把用户级权限落到现有 `permissions_json`/成员管理机制，至少支持：`VIEW_DATA`、`REQUEST_DATA`、`APPROVE_AUTHORIZATION`、`MANAGE_RULES`、`MANAGE_MEMBERS`。批准权限和查看权限互不自动包含；撤销后立即影响未来读取和调用。

更新 `backend/app/seed.py`、`backend/app/demo_seed.py` 和角色矩阵文档：保留 `REGULATOR`，为演示用户配置明确的用户权限；不要新增“数据授权管理员”角色。

### 3. 把连接器改成本地主体节点协议

#### 3.1 节点身份和路由

在 `connector/app/main.py` 增加 `ORGANIZATION_ID` 和节点标识校验。节点的签名身份是“主体节点”，不是能源领域；同一领域的不同企业必须使用不同节点身份、不同本地数据库/数据目录和不同密钥。

在后端设置中把当前按 `energy_domain -> endpoint` 的配置升级为 `org_id -> endpoint/public_key`；兼容旧配置仅用于迁移和演示，业务执行路径不得再根据能源领域猜测数据所有者。

保留现有请求签名、时间戳、nonce、查询预算和结果签名机制，扩展签名载荷包含 `provider_org_id`、请求项 ID、规则版本/审批依据和输出约束。节点遇到主体不匹配、规则不匹配、已撤销请求、过期 nonce 或不支持的输出时必须拒绝。

#### 3.2 本地计算和失败语义

节点只读取本地数据库，在本地完成均值、方差、总量、趋势和脱敏统计；返回结果摘要、统计值、计算版本、结果哈希、节点签名和执行回执，不返回原始行数据。

后端在 `backend/app/routers/trusted_query.py` 和查询服务中实现：

- 节点离线/超时：子请求保持 `PENDING_RETRY` 或进入明确失败态，不从中央数据库补读。
- 同一请求项重试：复用幂等键，返回已有回执，不生成第二次授权或第二份结果。
- 节点返回拒绝：记录拒绝原因，父请求不伪装成成功。
- 多主体请求：每个主体独立执行；全部必需主体成功才标记完整；允许部分结果时明确列出已批准、未批准和缺失主体。

为 `connector/tests/test_connector.py` 增加主体身份、签名载荷、规则命中、拒绝、重试和原始字段不出节点的测试。

### 4. 改造目录、规则和申请流

#### 4.1 目录和上传

在 `backend/app/routers/data.py`、`backend/app/services/vault.py` 和目录服务中区分：

- 生产路径：上传/采集进入主体本地节点，中央只登记资源目录元数据和数据版本指纹。
- 演示路径：使用明确标记为 synthetic/demo 的本地节点数据，不把它当成生产真实数据。
- 兼容路径：历史中央 vault 只允许迁移、审计和清理使用，不再作为新授权查询的原始数据来源。

所有拥有业务数据的主体角色都按 `org_id` 强制过滤目录；跨主体目录只展示名称、能源领域、资源名称、指标说明、时间范围、可用统计函数、规则摘要和数据更新时间，不展示具体数值。

上传后的数据版本保持不可变；上传前真实性不由系统承诺。页面和报告固定说明“基于主体上传数据，平台只验证上传后的完整性和计算过程，不等同于司法意义上的真实性认证”。

#### 4.2 预设规则

新增规则 CRUD 与版本化：企业有 `MANAGE_RULES` 的用户可设置并批准规则；每次修改产生新版本，旧版本只用于解释历史调用。

支持三种简单模式：

- 命中规则可自动调用。
- 必须企业审批。
- 禁止外部调用。

未配置规则默认必须企业审批。规则匹配至少检查指标、时间范围/粒度、统计函数、最小样本量、舍入/脱敏、频率/预算和主体。超出规则范围自动转为新申请，不通过已有规则。

### 5. 实现 REGULATOR 的完整跨主体流程

复用 `backend/app/services/data_usage_requests.py` 的申请、审批、拒绝、撤回、撤销和 `If-Match`/幂等机制，补齐父子请求：

1. `REGULATOR` 通过自然语言或表单描述主体、指标、时间范围、统计方式和用途。
2. Agent 只生成结构化草稿和按主体拆分预览，显示命中的规则、需要企业审批的项目和预期输出；不提交、不批准、不扩大范围。
3. `REGULATOR` 人工确认后，系统创建一个父请求和每个主体一个独立请求项。
4. 命中规则的请求项进入节点执行；未命中规则的请求项进入目标企业审批。
5. 每个企业只能审批自己的请求项；授权范围包含企业、指标、时间、函数和输出形式。
6. 执行完成后只回传授权范围内的聚合/脱敏结果和存证；能源局是否对外公布不进入本系统审批流。
7. 撤销规则或授权只阻止未来调用，不篡改已经生成的结果和审计。

在 `backend/app/routers/trusted_query.py` 增加或复用确认接口的严格校验：确认令牌必须绑定用户、原始查询、请求项范围和有效期；服务器再次检查当前权限、规则/审批状态和主体节点身份，不能只相信前端预览。

### 6. 结算和旧任务隔离

在现有结算/隐私计算任务服务上加统一任务状态和 scope 规则：

- 新结算每次创建独立任务 ID、数据版本指纹、请求授权和执行回执。
- 旧任务保留只读审计记录，但从当前任务列表、指标、授权复用和新计算中排除。
- 不提供“修正原任务”“替换原结果”“沿用原授权”的接口。
- 发现上传错误时，只能重新上传并发起全新结算；新旧任务之间不建立业务关联。

对 `backend/app/seed.py` 和运行时数据执行一次受保护的演示数据重置：只清理运行时数据库、vault、旧结算/授权/审计/模拟记录，保留代码、设计文档、测试、账号和角色。重置命令必须要求非生产演示环境标记，不能在生产环境执行。

### 7. 前端按主体和权限重构工作台

保持现有视觉系统和路由外壳，在 `frontend/src/access.ts`、`frontend/src/types.ts`、`frontend/src/components/layout.tsx` 和 `frontend/src/features/trusted-energy/` 中改为“角色 + `org_id` + 用户权限 + 任务 scope”共同决定可见内容。

#### 企业/能源主体工作台

展示自己的目录、节点健康、数据版本、规则、授权审批、自己的结算、自己有权查看的结果和存证。看不到其他企业的数值、原始目录数据和无关审计。

#### REGULATOR 工作台

展示全局目录元数据、Agent 输入区、拆分预览、确认按钮、申请进度、已授权结果和可见存证。目录页不显示具体数据值；未批准请求显示为等待/拒绝，不显示结果。

#### ADMIN 工作台

只展示系统健康、节点在线状态、队列、错误和部署信息，不展示企业业务数据。

每个操作都实现完整状态：`idle`、`loading`、`pending_approval`、`pending_retry`、`success`、`rejected`、`revoked`、`offline`、`error`。按钮权限不足时隐藏或禁用并解释原因；前端不自行拼接成功结果，不绕过服务端 scope。

新增前端测试覆盖：主体隔离、权限差异、目录无数值、Agent 必须人工确认、审批前无结果、撤销后不可调用、部分结果明确缺失、节点离线重试和存证范围。

### 8. 存证和审计可见性

主体本地节点保留完整本地审计；中央只保存控制面证据和最小必要投影：

- 谁发起了什么请求、作用于哪个主体。
- 命中了哪一版规则，或由谁在什么时间批准。
- 请求哈希、数据版本指纹、结果哈希、节点签名、平台执行回执和时间。
- 任务/主体/授权范围和可见性范围。

可见性规则固定为：

- 企业：本企业所有相关审计和本企业请求项。
- 交易参与方：自己参与任务所需的最小证据。
- `REGULATOR`：自己发起且已授权的请求、结果和对应存证；不能因监管角色直接打开所有企业完整审计。
- 社会公众：系统不直接给公众企业原始数据，只能看到能源局系统外部发布的聚合报告（如未来接入发布功能，则发布内容仍是能源局批准的聚合结果）。

Agent 中间推理不落库；只保存最终人工确认、实际执行、审批、撤销和结果回执。

### 9. 测试和验收

#### 后端

- 单元测试：scope、权限、规则版本、主体路由、哈希/签名、幂等和旧任务隔离。
- API 测试：不同能源主体互查必须 403/空结果；`REGULATOR` 只能看目录元数据；规则命中可执行，未命中进入审批；企业只能审批自己的请求项；撤销立即阻断未来调用。
- 集成测试：多主体父请求拆分、企业分别审批、本地节点计算、部分结果、节点离线重试和重复请求。
- 安全测试：中央没有原始数据回退；ADMIN、EXCHANGE、普通企业用户不能越权；篡改回执或错误节点签名必须失败。

#### 前端和连接器

- `pnpm typecheck`、`pnpm test`、`pnpm build`。
- 连接器测试验证 `ORGANIZATION_ID`、独立本地库、签名、规则、拒绝和原始数据不出节点。
- 至少一条浏览器/端到端脚本走通：目录 → Agent 拆分 → 人工确认 → 企业审批 → 本地计算 → 聚合结果 → 存证可见性。

#### 验收场景

1. 发电企业 A 和发电企业 B 互相不能查看数据。
2. 发电企业与煤炭企业互相不能查看数据。
3. `REGULATOR` 能看到所有主体的目录说明，但看不到数值。
4. 规则允许的“每日发电总量均值/方差”可自动调用。
5. 没有预设规则的请求必须由对应企业审批；未审批前无结果。
6. 多企业请求按主体拆分，各主体只审批自己的部分。
7. 企业拒绝或撤销后不会产生可用结果；已完成结果和审计仍可按 scope 查询。
8. 错误上传只能重新发起全新结算，旧任务影响完全消除。
9. 节点离线不会从中央取原始数据，恢复后可按同一请求项重试。
10. 任何参与方只能得到自己需要的、未越权的存证。

### 10. Render/GitHub 发布核验

在本地完整测试通过后，再更新 `docker-compose.yml`、`render.yaml`、环境变量示例和部署说明：

- 生产部署配置以 `org_id -> 本地节点端点/公钥` 为准；真实节点部署在主体自己的内网/服务器。
- Render 只部署中央控制面和明确标记为 synthetic/demo 的节点模拟器；不接入企业真实内网，不上传真实数据和密钥。
- GitHub 只提交代码、迁移、测试、文档、配置模板和模拟数据；运行时数据库、vault、日志、密钥、真实数据和临时文件全部排除。
- 发布前运行敏感文件/真实数据扫描、Git 状态检查、构建、健康检查和完整冒烟流。
- 最后才提交并推送改造代码；Render 只在部署配置验证通过后更新。

## 分阶段交付顺序

按以下顺序实施，每阶段完成后运行对应测试并保持可回滚的小提交：

1. 模型/迁移/权限 scope 和主体节点配置。
2. 连接器节点身份、签名、幂等、规则执行和错误语义。
3. 目录元数据、主体本地数据路径和规则 CRUD。
4. 父子请求、企业审批、REGULATOR 查询确认和多主体执行。
5. 结算新任务隔离、旧运行数据重置和新模拟数据。
6. 前端工作台、权限按钮、进度/失败状态和存证视图。
7. 全量测试、部署配置、敏感数据扫描和 GitHub/Render 发布核验。

## 完成定义

只有同时满足以下条件才算完成：

- 后端、连接器和前端测试通过。
- 上述十个验收场景全部走通。
- 真实数据只在主体本地节点；中央和 Render 只有控制面信息及模拟数据。
- 所有跨主体结果都能追溯到请求项、规则/审批、节点签名和结果哈希。
- 撤销、拒绝、离线、重试和错误上传的行为与设计一致。
- GitHub/Render 发布内容经过扫描，不含真实业务数据、运行时数据库或密钥。
